## 1. 整体认知：嵌入式开发到底在干什么

嵌入式 Linux 开发和 PC 开发最大的区别：

| 维度 | PC 开发 | 嵌入式 Linux |
|------|--------|-------------|
| 编译 | 本机编译本机跑 | **交叉编译**，目标平台跑 |
| 资源 | 内存按 GB 算 | 内存按 MB 算，单核 |
| 显示 | X11/Wayland 桌面 | 多数是 **framebuffer** 裸显 |
| 部署 | 装包/拷文件 | **板端覆盖**，注意占用/只读 |
| 调试 | 本地 IDE 断点 | **串口/SSH + 日志 + 文件轮询** |

**核心心法：开发板就是一台"有显示器的、资源很少的 Linux 电脑"，一切 PC 上的 Linux 知识都适用，只是要时刻注意资源上限。**

### 必须掌握的基础知识清单

- **交叉编译**：工具链、`sysroot`、`-march`/`-mfpu` 目标架构、动态链接库依赖（这是入门第一关）
- **Linux 文件系统**：`/dev`（设备节点）、`/sys`/`/proc`（内核接口）、挂载、读写权限、rootfs 只读分区
- **构建系统**：`qmake`/`Makefile`/`CMake`，至少要能看懂 .pro 和 Makefile
- **进程管理**：`kill`/`nohup`/`ps`，板子上没有 systemd，自启动靠 `rc.local` 或 systemui
- **基本网络**：`ssh`/`scp`/`ifconfig`/`ping`，用于部署和远程调试
- **字符编码**：嵌入式常用 UTF-8，中文字体要显式指定路径

## 2. 开发环境三板斧：交叉编译 / 传输 / 调试

### 2.1 交叉编译

**核心工具链**（本项目）：

```
source /opt/fsl-imx-x11/4.1.15-2.1.0/environment-setup-cortexa7hf-neon-poky-linux-gnueabi
```

source 之后会设置 `CC`/`CXX`/`CFLAGS`/`LDFLAGS` 等，`make` 直接能用。

**几个关键点**：

1. **架构匹配**：IMX6ULL 是 **armv7-a + hard float + neon**。写汇编/内嵌汇编时不能用 v8 指令；`-march` 必须匹配，否则指令不识别或性能差。
2. **动态链接**：板端 lib 版本必须和 sysroot 一致。移植 PC 软件（如 SDL 1.2）时，**不要链接板端已有的系统库的版本冲突项**，要么静态链接要么整个依赖一起带上。
3. **qmake 交叉编译**：Qt 项目用现成 sysroot 里的 qmake（`qt5` 环境的），不要用宿主机 qmake。
4. **在板上要看是否缺 .so**：跑起来报 `cannot open shared object`，`ldd`（或 `readelf -d`）确认依赖。

### 2.2 传输部署（最常用操作）

```bash
# SSH 免密码自动化脚本(项目里 appflash.py 就是这么做的)
sshpass -p 密码 scp ./myapp root@192.168.1.20:/home/root/

# 覆盖 /opt/ui/src/apps/ 下的程序前, 先杀掉占用进程, 否则 "Text file busy"
killall -9 mytest supermary; cp new /opt/ui/src/apps/mytest
```

**血泪教训**：

- **Text file busy**：正在运行的 ELF 文件不能覆盖。先 `killall` 再 `cp`。
- **目标路径写不进**：某些目录只读或权限不够，先传到 `/home/root/` 再 `cp`。
- **传输/校验**：小屏设备部署后，`ls -la` 对比大小确认传完整。

### 2.3 调试三板斧

1. **日志**：板端 `nohup ./app > /tmp/log 2>&1 &`，再 `ssh tail -f /tmp/log`。QML 的 `console.log` 会进 stderr。
2. **grep 过滤**：`grep -a "关键字" /tmp/log | tail`，日志量大时按关键字筛。
3. **进程状态**：`ps -o pid,args` 确认进程活着、`top` 看 CPU。

**调试方法论：改代码 → 交叉编译 → 传板 → 跑 → 看日志 → 再改。** 板端没有断点调试的条件（除非接 gdbserver），所以**日志点要打得多、打得准**，尤其怀疑"某个分支没走到"时，直接 `qDebug()/console.log` 打标记。

## 3. 显示系统：framebuffer / Qt / 分辨率适配

### 3.1 三层显示栈

```
App(Qt/QML) → Qt 平台插件(linuxfb) → /dev/fb0(framebuffer) → LCD 控制器
```

- 板子 800×480，**无 X11/Wayland**，Qt 用 `linuxfb` 平台直接画到 framebuffer。
- 查看分辨率：`cat /sys/class/graphics/fb0/virtual_size` 或 `fbset`。
- 启动 Qt 程序固定平台参数：

```bash
export QT_QPA_PLATFORM=linuxfb:tty=/dev/fb0
export QT_QPA_FONTDIR=/usr/share/fonts/ttf   # 中文字体路径
./mytest fight
```

### 3.2 移植游戏/软件时的分辨率适配（核心经验）

原版是 800×545 或 640×480 的游戏，要适配 800×480 屏幕，有三种做法，**从简单到复杂**：

1. **整体缩放**：`painter.scale()` 把画布压到屏幕尺寸。简单但**比例失真**（游戏会被压扁/拉伸）。
2. **坐标裁剪**：固定显示区域，裁掉不可见部分。适合场景本身比屏幕大。
3. **相机/视口平移**：世界坐标不变，用一个 camera 偏移量控制"看哪里"。这是 2D 横版游戏的标准做法。

**本例实战**（`gamescene.cpp` paintEvent）：

```
// 1. 相机带死区: 玩家在屏幕中间 110px 内移动, 画面不动, 超出才平滑跟随
//    消除"画面跟着人物一抖一抖"
// 2. 垂直锚定地面: 跳跃时画面不上下晃
// 3. 锚点缩放: translate(ax,ay); scale(1.25); translate(-ax,-ay) 实现局部放大
```

**心得**：游戏画面"小、晃、被压扁"是最常见的三个观感问题，分别对应缩放、相机死区、宽高比三个概念。

### 3.3 Qt 字体与中文

- 不设字体目录：中文全是方块。
- `QT_QPA_FONTDIR` 指向含中文字体的目录；程序里 `QFont("Times", ...)` 对中文可能无效，要指定支持中文的字体。
- **嵌入小屏不要用超大字号**：HUD 用 22px 就很清晰，40px+ 会相互重叠（本项目踩过"第X关"和"时间"文字重叠的坑）。

## 4. 外设与输入：GPIO / 触摸 / USB 手柄

### 4.1 触摸屏

- 设备节点：`/dev/input/event1`（`cat /proc/bus/input/devices` 确认）。
- Qt 里要设 `TSLIB_TSDEVICE=/dev/input/event1`、`QT_QPA_FB_TSLIB=1`。
- **触摸点不匹配屏幕**：调 `/etc/pointercal` 或 tslib 校准。

### 4.2 USB 手柄（本项目最大坑）

**硬件**：XBOX360 克隆手柄，USB 直连。问题：固件和板子的 `ci_hdrc` USB 控制器间歇性不兼容，SDK 读到的事件可能错乱。

**方案（通用思路）**：**不要让每个 App 直接读 USB，让一个常驻守护进程独占设备，把状态写文件/广播给所有 App。**

```
gamepadd(守护进程, 独占USB) ──> /tmp/gamepad.sock (本地socket)
                               └──> /tmp/pad_state  (文本文件, 供SDL等程序读)
```

- Qt 侧：`QLocalSocket` 连 `/tmp/gamepad.sock`，按行解析 20 个字段。
- SDL/其它程序：**不要复用 socket fd**（SDL 会误关 fd），改为**轮询读 `/tmp/pad_state` 文件**。
- 手柄数据格式：`lx,ly,rx,ry,lt,rt,a,b,x,y,lb,rb,start,back,ls,rs,up,down,left,right`，20 个字段。
- **摇杆有正负**：`LY 上推为正(+32767)，下推为负(-32768)`，写游戏判断方向时别搞反。

**通用心法：外设驱动这件事，优先"一个进程独占+对外广播状态"，而不是"每个程序都抢设备"。**

### 4.3 按键输入要统一抽象

小屏设备输入法很杂（触摸、手柄、键盘），**每个页面必须同时支持至少两种**：

- 菜单/按钮：触摸 `onClicked` + 手柄 `A 确认 / 方向导航`
- 游戏内：手柄 + 触摸按钮叠加
- **手柄导航要用"边缘触发"**（按下瞬间移动一次），不要按住连跳，否则用户稍一长按就到底了。

## 5. 性能优化：单核 528MHz 的生存之道

### 5.1 先测再说

- 移植过来的引擎/游戏，**先在板子上跑个基准**（`top` 看 CPU、帧率计数器），确认瓶颈。
- 本项目 OpenMugen 能跑 60fps，但发现角色控制器表大多为 NULL（引擎功能不完整），说明"能跑"≠"能用"。

### 5.2 优化手段（按性价比排序）

1. **降低绘制分辨率**：用 `painter.scale()` 绘制比每像素精确绘制快得多。
2. **减少每帧全量重绘**：QML Canvas 全屏重绘在单核上很贵；考虑分区域或降低刷新频率。
3. **定时器频率**：游戏循环 `interval` 从 15ms→20ms 视觉几乎无差但 CPU 省 25%。
4. **动画用 QML 内置 Behavior/NumberAnimation**（QPainter/引擎合成），不要每帧手写 update()。
5. **静态资源预先缓存**：图片/字体只加载一次，别在 paintEvent 里 `QPixmap(":/...")` 每次新建。

### 5.3 手感与性能的平衡

- 攻击判定、击退、受伤无敌帧等"手感"参数，**先用调参工具**（把值写文件，程序热读），满意后再固化。
- AI 太强/太准会让玩家沮丧：给 AI 加**随机失误（挥空概率）、更长攻击间隔、发呆动作**，观感立刻真实。

## 6. UI/交互设计：小屏上的可用性

- **按钮要大**：800×480 上最小可点区域 ≥60×40，本项目 TouchBtn 默认 72×72。
- **文字要小、要分行**：HUD 信息多时，字体 20-24px，不同信息分行，**别把两个数值画在相邻很近的位置**（重叠是必然）。
- **触摸 + 手柄都要支持**：用户会换着用，单一输入会让设备"很奇怪"。
- **游戏内要能随时退出**：暂停/退出按钮要常驻可见，不要指望用户记得某个手柄键。
- **菜单层级**：选关、暂停、返回的层级要浅，1-2 级即可。

## 7. 调试排障方法论

### 7.1 经典问题速查

| 现象 | 原因 | 排查 |
|------|------|------|
| Text file busy | 程序正在运行 | `killall` 后再覆盖 |
| 画面被压扁 | 宽高比不匹配 | 用相机/裁剪而非纯 scale |
| 中文方块 | 没设字体目录 | `QT_QPA_FONTDIR` |
| 触摸无反应 | 设备节点/校准 | `cat /proc/bus/input/devices`、tslib |
| 手柄数据错乱 | USB 协议不兼容 | 守护进程独占 + 重连/复位 |
| 摇杆方向反了 | 轴正负理解错 | 打印裸值确认 |
| 程序闪退 | 缺 .so 或段错误 | `ldd`、stderr 日志 |
| 长按菜单连跳 | 无边缘触发 | 加 prev 状态判断 |
| 游戏结束无反应 | 事件被遮挡/分支没走到 | 加 console.log 标记 |

### 7.2 调试原则

1. **一次只改一个变量**：尤其手感/性能类问题。
2. **加日志确认"走到了"**：怀疑分支，直接打标记，别猜。
3. **先本地复现再上板**：PC 上先把逻辑调通，板子只做移植验证。
4. **保留对比**：改之前 `git diff`/备份，改坏了能回退。
5. **读 dmesg**：USB、驱动类问题 `dmesg | tail` 往往直接给出答案。

## 9. 心得体会

### 9.1 关于"移植"

**移植不是"复制代码"，而是"理解它的世界坐标系、事件循环、资源加载，然后在目标平台上重画一遍"。**

本项目移植 SuperMario 的经验：核心是搞懂它的**坐标体系**（800×545 世界坐标、相机如何跟随）、**事件来源**（键盘事件 vs 手柄轮询）、**绘图时机**（定时器驱动 update）。这三件事搞通了，加功能（选关、暂停、退出）都只是往正确的位置插代码。

### 9.2 关于"学习路径"

对 IMX6ULL 这类入门板，**正确的路径**是：

1. **先跑通一个最小例程**（GPIO 点灯 / Qt 显示一张图），建立"编译→部署→运行"的闭环。
2. **读懂一个中型项目**（如本项目 qt_dev 的 systemui + 一个 App），理解工程结构。
3. **自己动手改**（加个按钮、换个颜色），感受"改一处→重新编译→传板→看效果"的节奏。
4. **再挑战移植/自研**：把 PC 上的一个游戏或库搬到板子上，会踩光所有的坑，也就学会了。

### 9.3 关于"调试心态"

- 嵌入式调试**慢**，一次迭代可能 1-2 分钟，所以要**减少迭代次数**：多打印、多想、少盲改。
- **别跟设备较劲**：硬件/固件的问题（如 USB 兼容）该绕过就绕过，用软件方案（守护进程、轮询文件）规避。
- **性能问题先量化**：一上来就"优化"往往瞎忙，先确认瓶颈在哪。

### 9.4 最后

嵌入式 Linux 开发的核心，无非是"**交叉编译 + 资源受限 + 真机调试**"三个关键词。把这三点变成肌肉记忆，剩下的就是普通 Linux + C/C++ + 具体框架（Qt/GTK/裸机）的知识积累。**看得懂原理、上手能跑、踩坑能扛**，这就是这门手艺的全部。
