第 17 课：CAN 报文格式与仲裁

标准帧/扩展帧/遥控帧：读懂总线上流动的每一个位（瑞萨《CAN 入门教程》第 7~8.7 章）

本课目标：上一课认识了"线"，这一课认识"话"。学完你能说出 CAN 的五种帧、画出标准数据帧 7 个段的完整位布局，说清扩展帧 29 位 ID 与标准帧 11 位 ID 的区别，并会用手算推演"两个节点同时发消息，谁赢得仲裁"。

1. 标准规格：ISO11898 vs ISO11519-2

CAN 协议经 ISO 标准化后有两套物理层规格（PDF p.12~16）：

ISO11898（高速）ISO11519-2（低速容错）
通信速度最高 1Mbps（常用 125k~1M）最高 125kbps（10k~125k）
总线长度40m / 1Mbps1km / 40kbps
连接单元数最大 30最大 20
总线拓扑闭环总线 + 120Ω 终端电阻开环总线 + 2.2kΩ 终端电阻
数据链路层两种规格定义相同（所以报文格式一脉相承）

按 SAE 分类：Class A（车身，10kbps）→ Class B（状态信息，10k~125k）→ Class C（实时控制：发动机/ABS/悬挂，125k~1M）→ Class D（多媒体，走 MOST/FlexRay）。你要做的是 F407 的高速 CAN，对标 Class C。

2. 帧类型总览

CAN 通信靠 5 种帧（PDF p.17~18）：

  • 数据帧：发送单元向接收单元传送数据
  • 遥控帧：接收单元向具有相同 ID 的发送单元请求数据
  • 错误帧：检测出错误时向其它单元通知错误
  • 过载帧：接收单元通知"我还没准备好接收"
  • 帧间隔：把数据帧/遥控帧与前面的帧隔开

数据帧和遥控帧又有两种格式：标准格式（11 位 ID）和扩展格式（29 位 ID）。STM32 bxCAN 默认用标准格式，够用且省带宽。

3. 数据帧详解：7 个段

数据帧由 7 个段构成（PDF p.21~27）：

# 标准数据帧（8 字节数据，不含填充位时共 47 位）
┌──────┬────────────────────┬─────────────┬──────────────────────┬──────────────┬──────────┬────────┐
│ SOF  │     仲裁段          │  控制段      │      数据段          │   CRC 段     │  ACK 段  │  EOF   │
│ 1 位 │ 11×ID + 1×RTR       │ 1×IDE 1×r0  │  0~8 字节            │ 15+1 位      │ 1+1 位   │ 7 位   │
├──────┼────────────────────┼─────────────┼──────────────────────┼──────────────┼──────────┼────────┤
│显性 0│ ID 从高位到低位      │ 显性 显性    │ MSB 先行，最长 8 字节 │ CRC + 界定符 │ 槽+界定符│ 隐性×7 │
│      │ RTR=0 数据 / 1 请求 │ + DLC(4 位) │                      │              │          │        │
└──────┴────────────────────┴─────────────┴──────────────────────┴──────────────┴──────────┴────────┘
# DLC = 数据长度码，与字节数对应：0~8；CRC 计算范围 = SOF~数据段
  • SOF（帧起始）：1 个显性位，宣告"我要发帧了"
  • 仲裁段：11 位 ID（从最高位 ID28 依次发出）+ 1 位 RTR。RTR 显性(0) 表示数据帧，隐性(1) 表示遥控帧。禁止 ID 高 7 位全为隐性（即 ID=1111111xxxx 不允许）
  • 控制段：IDE + r0（保留位，发显性）+ 4 位 DLC，表示数据字节数 0~8
  • 数据段：0~8 字节，从 MSB 开始发
  • CRC 段：15 位 CRC 序列 + 1 位 CRC 界定符（隐性），用于检传输错误
  • ACK 段：发送方发 2 个隐性位；接收方在 ACK 槽里回 1 个显性位表示"收到且没错"——这就是著名的"返回 ACK"
  • EOF（帧结束）：7 个隐性位

扩展帧只是把仲裁段拉长：11 位基本 ID + SRR + IDE + 18 位扩展 ID + RTR，共 29 位 ID，其余段与标准帧相同（PDF p.22~23）。29 位 ID 空间更大，适合复杂的工业协议（CANopen 等常用扩展帧）。

4. 遥控帧：伸手要数据

遥控帧用来请求数据（PDF p.28~29）：它只有 6 个段——没有数据段！结构 = SOF + 仲裁段 + 控制段 + CRC + ACK + EOF，其中 RTR=1（隐性）。"请把 ID 和我一样的那份数据发给我。"对方节点看到后回一个同 ID 的数据帧。

5. 错误帧与过载帧

错误帧：检测出错误的节点立刻输出错误标志（PDF p.30, 39）。主动错误状态输出 6 个显性位的错误标志，之后是 8 个隐性位的错误界定符。发送方发完错误帧后会重新发送刚才失败的帧。

过载帧：接收方"忙不过来"时输出，结构与错误帧相同（6 显性 + 8 隐性），作用只是让对方等一等（PDF p.31）。

6. 帧间隔：帧与帧之间的喘息

帧间隔用于把数据帧/遥控帧与前面的帧分开（PDF p.32）：

  • 间隔：3 个隐性位
  • 总线空闲：隐性电平，长度不限（可为 0）——此时任何单元都可开始访问总线
  • 延迟传送：8 个隐性位，只有处于被动错误状态的单元发完一个消息后才插入（防止它霸占总线）

7. 优先级仲裁：谁先赢

总线空闲时最先开始发的单元获得发送权；多个单元同时开始发送时，从仲裁段第一位起逐位仲裁（PDF p.33~35）：

  • 规则一句话：连续输出显性电平最多的单元继续发送，输的立刻转为接收——所以 ID 越小优先级越高
  • 同一 ID 的数据帧 vs 遥控帧：最后一位 RTR，数据帧是显性(0)，数据帧赢
  • 同一 ID 的标准帧 vs 扩展帧：标准帧的 SRR 位是显性，标准帧赢

💡 记忆锚点：CAN 的 ID 不是"门牌号"，是"优先级号码"——数字越小越靠前。0x000 相当于总冠军，0x7FF 只能等大家都发完。设计命令帧时，越紧急的 ID 越小。

⚠️ ID 规划要避开禁区：标准帧禁止高 7 位全为隐性（ID = 1111111xxxx 即 0x7C0~0x7FF 之间不可用），否则仲裁会出错。另外，数据帧和遥控帧共享同一个 ID 空间——同 ID 的"请求"和"应答"别混着用。

代码示例

下面两段代码：第一段把一个命令封装成"标准帧"的概念模型（对应 STM32 的 CAN_TxHeaderTypeDef），第二段模拟逐位仲裁。

/* 一个 CAN 标准帧的"概念模型"（HAL 里对应 CAN_TxHeaderTypeDef） */
typedef struct {
    uint32_t StdId;   /* 11 位标准 ID：0x000 ~ 0x7FF */
    uint8_t  RTR;     /* 0=数据帧, 1=遥控帧 */
    uint8_t  DLC;     /* 数据长度码：0~8 */
    uint8_t  Data[8]; /* 数据内容，最多 8 字节 */
} CAN_StdFrame;

/* 填充一帧"播放曲目"命令：ID=0x123，数据=2 字节曲目号 */
void fill_play_frame(CAN_StdFrame *f, uint16_t track_no)
{
    f->StdId   = 0x123;                 /* 命令帧 ID */
    f->RTR     = 0;                     /* 数据帧 */
    f->DLC     = 2;                     /* 2 字节数据 */
    f->Data[0] = (uint8_t)(track_no >> 8); /* 曲目号高字节（MSB 先行） */
    f->Data[1] = (uint8_t)(track_no);      /* 曲目号低字节 */
}

/* 模拟逐位仲裁：从最高位开始比，显性(0)获胜 */
/* 返回 1 表示 id_a 赢得仲裁 */
int arbitration_winner(uint16_t id_a, uint16_t id_b)
{
    int bit;
    for (bit = 10; bit >= 0; bit--) {        /* 标准帧 11 位，从 ID28 开始 */
        int a = (id_a >> bit) & 1;          /* 0 = 显性, 1 = 隐性 */
        int b = (id_b >> bit) & 1;
        if (a != b)
            return (a == 0);                 /* 先出现显性(0)的赢 */
    }
    return 1;                                /* ID 相同，继续比 RTR 等 */
}

/* 例：节点 A 发 0x188，节点 B 发 0x123，谁赢？ */
int winner = arbitration_winner(0x188, 0x123);   /* 1 → 0x123 赢 */

随堂小测

Q1. 标准格式数据帧的 ID 是多少位？

A. 8 位，和 UART 地址一致

B. 11 位，表示消息优先级

C. 29 位，全部用于寻址

查看答案
B。标准格式 11 位 ID，不是地址而是优先级（PDF p.17, 23）。

Q2. 数据帧 DLC 最大能表示几个字节的数据？

A. 最多 8 字节（DLC=8）

B. 最多 4 字节（DLC=4）

C. 最多 16 字节（DLC=16）

查看答案
A。数据段 0~8 字节，DLC 与字节数对应表见 PDF p.24 表 8。

Q3. 相同 ID 的数据帧和遥控帧竞争时，谁赢？

A. 遥控帧，因为它更轻量

B. 数据帧，因为 RTR 是显性

C. 先发出去的赢，与帧型无关

查看答案
B。仲裁段最后一位 RTR，数据帧为显性(0)，显性覆盖隐性所以数据帧获胜（PDF p.34）。

Q4. 接收方"返回 ACK"是怎么做的？

A. 在 ACK 槽发送一个显性位

B. 发一帧专用的应答帧

C. 提高自己的 ID 优先级

查看答案
A。接收方在 ACK 槽（发隐性位的位置）回一个显性位，表示正常接收（PDF p.26）。
