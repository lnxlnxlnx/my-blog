接口适配层与基础设施层

DDD 与六边形架构 · 课程 0009 · 预计 25 分钟

最外两层的收尾:① 接口适配层(Interface Adapters)——接收/回应用户的控制器(controller)与数据传输对象 DTO;② 基础设施层(Infrastructure)——仓储(repository)实现、持久化模型、外部适配器。本课把这两层拼完,你的六边形就完整了。

知识点 1:控制器——入口,把请求转成命令/查询

控制器是接收外部输入的地方(HTTP 路由、CLI、事件都用它)。它不做业务,只做三件事:解析输入、转成命令/查询、交给应用服务,再把结果包成响应:

class UserController:                       # 接口适配层
    def __init__(self, bus: CommandBus):
        self.bus = bus
    def create_user(self, request):
        email = request["email"]            # 解析
        cmd = CreateUserCommand(email=email, name=request["name"])  # 转命令
        user_id = self.bus.execute(cmd)     # 交给应用层
        return {"id": user_id}              # 返回响应

控制器不该懂领域规则,它只是"翻译官"——把外部世界翻译成命令/查询,再把结果翻回去。业务逻辑一点不在这层。

知识点 2:DTO——跨边界的"传输壳"

DTO(Data Transfer Object)是明确为传输而设的数据对象,别把实体/值对象直接丢出边界(会泄漏领域内部)。分两种:

# 请求 DTO:进来的输入壳
@dataclass
class CreateUserRequestDTO:
    email: str
    name: str

# 响应 DTO:出去的输出壳(不暴露内部 id/wallet 等)
@dataclass
class UserResponseDTO:
    id: str
    email: str

重要原则:值对象/实体不要放进 DTO/事件/数据库模型——跨传输前先序列化成基本类型(项目明确警告,回顾 0004)。DTO 是边界的"快递盒",领域对象是"货物",出去前要打包。

知识点 3:仓储 Repository——端口还是实现?

仓库分两层角色:端口(领域层声明的接口,0008 讲过)和实现(基础设施层)。数据映射发生在实现处:

# 端口(在应用/领域层)
class UserRepository(ABC):
    @abstractmethod
    def save(self, user) -> None: ...
    @abstractmethod
    def find_by_id(self, user_id) -> "User | None": ...

# 实现(在基础设施层):负责 领域对象 ↔ 持久化行 的转换
class SqlUserRepository(UserRepository):
    def find_by_id(self, user_id):
        row = self.db.query_one("SELECT * FROM users WHERE id = ?", user_id)
        if row is None: return None
        return User(id=row["id"], email=Email(row["email"]))   # 行→领域
    def save(self, user):
        self.db.execute("INSERT ... ", user.id, user.email.value)  # 领域→行

仓储的唯一职责本来是"按聚合根存取";注意查询(读)可绕过仓储直查库(0007),这是项目的取舍。别把仓储变成"万能数据访问层"。

知识点 4:持久化模型 vs 领域模型

数据库的表结构(持久化模型)和领域模型不必相同。项目建议:领域实体按"业务逻辑建模",持久化时再映射到 DB schema;不要让领域去向数据库妥协。说白了——领域数据该为业务建模,不是为表建模(对比贫血模型)。

知识点 5:基础设施里还装什么

除仓储实现外,基础设施层还放:外部 API 客户端、消息队列发送方、发邮件、日志落地等"适配器"。它们都是端口的实现,依赖注入进应用/领域层。至此六边形完整闭环:控制器→应用服务→领域,数据经由端口/适配器进出,依赖始终向内。

测一测(先自己答,再点答案)

测验 1

控制器该不该含业务规则?

控制器只做翻译:解析输入→转命令/查询→交应用层,不含业务规则。

测验 2

DTO 里能不能直接放实体?

跨传输/序列化前先把领域对象转基本类型,别裸漏实体/值对象出边界。

测验 3

领域对象 ↔ 数据库行 的转换在哪?

仓储实现(基础设施层)负责领域对象与持久化行互转。

测验 4

领域模型与 DB 表结构?

领域实体按业务建模,持久化时映射到 DB,不必与表结构相同。
