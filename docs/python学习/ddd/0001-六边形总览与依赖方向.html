六边形架构总览与依赖方向

DDD 与六边形架构 · 课程 0001 · 预计 20 分钟

你要学的 [domain-driven-hexagon](https://github.com/Sairyss/domain-driven-hexagon) 把好几种架构揉在一起:Domain-Driven Design(DDD)、Hexagonal(端口-适配器)、Clean / Onion、SOLID。听着吓人,但它们共享同一个骨架。这一课先搭起骨架,之后 0002~0010 逐个填空。

知识点 1:五个词其实是一个意思——依赖指向内

别被术语吓到。这些架构都在说同一件事:

# 一层叠一层,核心在最里层:
#   基础设施 → 接口适配器 → 应用层 → 领域层(最核心)
#   (数据库/外部API)   (控制器)   (用例)     (业务规则)

规则只有一条:依赖只能从外层指向内层;内层永不依赖外层。领域层(最核心)不知道也不关心你用的是 MySQL 还是 Postgres、是 HTTP 还是 CLI——这些「外部细节」都塞到最外层。

知识点 2:为什么——测试和换实现都容易

因为领域层不依赖外部,你就能:① 不连数据库就能测业务(用假数据/替换实现);② 换数据库/加新接口时不碰业务代码。这就是「六边形」/「洋葱」/「整洁」共同的卖点(Clean Architecture、Hexagonal、Onion)。

知识点 3:数据流长这样(从左到右)

项目 README 给的数据流,翻译成顺序:

# 1 请求/命令 → 控制器(接口适配层)
# 2 控制器把请求解析成 Command/Query,交给应用服务
# 3 应用服务：调领域对象(实体/聚合/领域服务)执行业务逻辑;
#   需要外部数据/发送事件时,通过「端口」(接口)去取
# 4 基础设施层：用具体实现(ORM/数据库/外部API/消息队列)完成端口要求,取完/存完转回领域格式
# 5 应用服务返回结果 → 控制器 → 返回给用户

记忆:入口在控制器,逻辑在应用服务,规则在领域层,细节在基础设施。你之前的架构课(分层架构 0009)讲的就是这道方向。

知识点 4:项目里的分层怎么放文件

项目 src/modules 按模块(module,也叫 bounded context 的有边界领域)组织,每模块内部再分领域/应用/接口/基础设施。用 Python 看形状:

# src/modules/user/                  ← user 业务模块
#   ├── domain/                      ← 领域层(最核心)
#   │   ├── user.entity.py           ← 实体
#   │   ├── value-objects/           ← 值对象
#   │   └── events/                  ← 领域事件
#   ├── application/                 ← 应用层
#   │   ├── commands/                ← 命令(用例)
#   │   ├── queries/                 ← 查询(读)
#   │   └── ports/                   ← 端口(接口)
#   ├── interface/                   ← 接口适配层
#   │   └── controllers/  dto/       ← 控制器 / 数据传输对象
#   └── infrastructure/              ← 基础设施层
#       ├── database/                ← 仓储实现、持久化模型
#       └── adapters/                ← 适配器

这个目录形状你会在无数真实项目里见到。现在只需记住每层放什么:领域放规则、应用放用例、接口放控制器、基础设施放数据库/外部。

知识点 5:什么时候别用这套(很重要)

项目 README 明确警告:这套完整架构不适合单纯 CRUD、业务逻辑不多的小项目——前期多出大量样板和抽象,反而过度复杂。它适合业务复杂、要长期演进、多团队的系统。你学它,是为了读懂大项目;自己写小工具别硬套(过度抽象反模式)。

测一测(先自己答,再点答案)

测验 1

依赖只能从哪指向哪?

依赖只从外层指向内层;内层永不依赖外层。这是六边形/洋葱/整洁共同的核心。

测验 2

「业务规则」放哪一层?

业务规则放最核心的领域层,不依赖框架/数据库/外部。

测验 3

「数据库选 MySQL 还是 Postgres」是哪种细节?

数据库/框架/外部API都是基础设施细节,塞最外层,领域层不关心。

测验 4

这套完整架构最适合哪种项目?

适合业务复杂、长期演进的大系统;简单 CRUD 硬套会过度设计。
