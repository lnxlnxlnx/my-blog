观察者模式:状态变了通知大家

架构与设计模式 · 课程 0006 · 预计 20 分钟

训练一轮,日志要打印、进度条要动、TensorBoard 要画、早停要判断……你有没有想过这些「跟班」是怎么被通知的?答案就是本课主角——观察者模式(Observer),也叫发布-订阅(Publish-Subscribe)。它是所有「回调 / 事件 / 信号」的底子。

知识点 1:问题的样子——硬编码通知

没有观察者模式时,「通知」是写死的:每加一个想被通知的模块,就得回去改训练代码:

def train(model, X, y, epochs=10):
    for epoch in range(epochs):
        loss = model.fit(X, y)
        logger.log(f"epoch {epoch}: {loss}")     # ① 写死的日志
        progress_bar.update()                    # ② 写死的进度条
        trboard.add_scalar("loss", loss)         # ③ 写死的可视化
        if loss < THRESHOLD:                     # ④ 写死的早停
            early_stop(epoch)
# 想加第 5 个跟班(比如微信告警)?→ 又回来改 train() 一行行插

问题:train 知道所有跟班的存在,耦合一大堆;跟班多了,主流程被插得支离破碎。

知识点 2:观察者模式——订阅与通知

把关系反过来:跟班们主动登记(订阅),主对象只管广播(通知),谁在那听随它便(官方讲解):

class Trainer:
    """被观察者(Subject):手里攥着一份订阅名单。"""
    def __init__(self, model):
        self.model = model
        self._observers = []                     # 订阅名单

    def subscribe(self, callback):               # 观察者自己来挂号
        self._observers.append(callback)

    def _notify(self, **event):                  # 广播:逐个打电话
        for cb in self._observers:
            cb(**event)

    def train(self, X, y, epochs=10):
        for epoch in range(epochs):
            loss = self.model.fit(X, y)
            self._notify(epoch=epoch, loss=loss)  # 唯一通知点


# ---- 观察者:各自就是一个回调函数 ----
def log_event(epoch, loss):
    print(f"epoch {epoch}: {loss:.4f}")

def early_stop_event(epoch, loss):
    if loss < 0.15:
        print(f"  已达目标,第 {epoch} 轮早停!")

trainer = Trainer(model)
trainer.subscribe(log_event)                  # 登记
trainer.subscribe(early_stop_event)           # 想加跟班?加一行 subscribe

对比硬编码版:train 的代码从此再也不用改——加日志、加监控,都只是调用方多 subscribe 一行。这就是「通知逻辑」和「主流程」解耦。

知识点 3:Python 里它经常长成「回调参数」

很多库不叫 observer,叫 callback 或 on_xxx——本质一样。AI 生成的训练代码尤其普遍:

def train(model, X, y, epochs=10, on_epoch_end=None, on_train_end=None):
    for epoch in range(epochs):
        loss = model.fit(X, y)
        if on_epoch_end is not None:            # 空档期广播
            on_epoch_end(epoch=epoch, loss=loss)
    if on_train_end is not None:
        on_train_end(model=model)


# 使用方:自定义回调,像挂插件一样塞进来
train(X, y,
      on_epoch_end=lambda epoch, loss: print(epoch, loss),
      on_train_end=lambda model: save(model, "best.pth"))

参数列表里的 callbacks=[...]、on_xxx=...,背后都是观察者模式。Keras 的 callbacks、PyTorch Lightning 的 callbacks、sklearn 里的 callbacks,全是同一个套路。

知识点 4:和策略模式怎么区分

初学者容易混——都是「传一个函数进来」:

策略模式

主对象主动调用这个函数去完成一项工作(算折扣、排序)。一用一换。

观察者模式

主对象被动广播事件,函数们自己决定要不要响应、响应几次。一群收听者。

一句话:策略是「换个干活的人」,观察者是「喊一嗓子,爱听的来听」。

知识点 5:什么时候别用

  • 只有 1 个跟班、永远不变 → 直接函数调用更清楚
  • 回调层层嵌套、没人说得清执行顺序时 → 观察者也会变成一团乱麻(回调地狱),此时该考虑别的手段
  • 判断标准:跟班数量会增长 / 变化,才值得做成订阅/广播。

测验 1

观察者怎么被通知?

观察者先在订阅名单里登记,状态变化时被通知者会逐个调用其回调(订阅 + 广播)。

测验 2

Python 里最常见形式?

训练 API 里的 callbacks=[...] / on_epoch_end=...,本质就是观察者:注册回调,事件时广播。

测验 3

观察者和策略区别是?

策略是「主对象主动调用一个算法」;观察者是「主对象广播事件,一群订阅者响应」。
