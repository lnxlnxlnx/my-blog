分层架构与依赖方向

架构与设计模式 · 课程 0009 · 预计 20 分钟

第一课我们说「架构 = 模块之间怎么组织、依赖朝哪个方向」。前面把招式学完,这课终于画出地图。分层架构(Layered Architecture)是最通用、最易懂的代码组织方式。

知识点 1:三条主线——表现 / 业务 / 数据

绝大多数程序可以切三层,你的 ML 项目也不例外:

表现层 Presentation

和人/系统打交道:CLI、API、notebook 入口、报表展示。

业务层 Domain

核心逻辑:训练、特征、评估、调参。不关心在哪儿展示、怎么存储。

数据层 Data

和外部资源打交道:数据库、文件、缓存、第三方 API。

规则只有一条:依赖只许向下——表现层可以依赖业务层,业务层可以依赖数据层;反过来禁止(数据层绝不该 import 表现层)。

知识点 2:为什么要单向依赖

# 坏:数据层偷偷碰到了表现层 —— 依赖向上,成一团乱麻
# data/loader.py
#   from ui.progress import show_progress   ← 数据层竟然依赖界面

# 好:数据层只管数据,不关心谁在看
# data/loader.py
#   def load(path, on_progress=None): ...   ← 最多收个回调,不 import 上层

单向依赖的价值:每一层可以单独改、单独测。表现层明天从 CLI 换 Web,业务层和数据层一行不动。依赖一旦成环,改 A 影响 B、改 B 又影响 A,没人敢动。

知识点 3:依赖方向的具体规则——高层依赖抽象

层与层之间连接时,遵守同一句话:高层策略依赖「约定」,不依赖「具体实现」。这正好用上前几课全部内功:

# 业务层的 Service 依赖接口,不依赖具体存储(依赖抽象):
class ExperimentService:
    def __init__(self, store):          # store 是「抽象/接口」,注入
        self.store = store
    def run(self, cfg):
        model = self._train(cfg)
        self.store.save(model)          # 不知道是 FileStore 还是 DBStore

# 数据层提供实现,并「向上」注册给业务层(反转控制):
file_store = FileStore()
service = ExperimentService(file_store)   # 组合点在这里

这就是依赖反转(Dependency Inversion):具体实现由最外层(组合根)组装后注入进来;业务层永远只认识接口。第一课的 make_trainer() 到第八课的构造器注入,全是这套思想。

知识点 4:一个 ML 项目目录长什么样

把三层化成目录,一目了然(Hitchhiker's Guide 结构建议):

my_project/
├── app.py                 # 组合根 + 表现层入口(CLI/API)
├── domain/                # 业务层:核心逻辑
│   ├── trainers.py        #   BaseTrainer / make_trainer
│   ├── features.py
│   └── metrics.py
├── data/                  # 数据层:IO / 存储 / 第三方
│   ├── loader.py
│   └── store.py
├── tests/                 # 测试(可以 mock 掉 data 层)
│   └── test_trainers.py
└── config.py              # 配置:传给组合根

按功能模块分组(一个功能一个包),比按层建三个大包更好用——因为「改一个功能」时,动的文件都在一处。依赖规则照旧:包之间只许向下。

知识点 5:判断你自己代码的依赖方向

回到第一课的四步法,第 2 步「画依赖」此刻升级了:画完箭头,问两个问题:

  1. 有没有向下的环?(A→B→A 就是环,要拆)
  2. 业务核心有没有漏到表现/数据层?(比如 app.py 里写训练循环 = 业务逻辑漏到入口)

AI 生成的代码最常见毛病,就是把业务逻辑全写在脚本/入口里。你能指出「这个入口太胖了,业务应该下沉」,就能帮团队重构——这就是参与复杂项目的基本功。

测一测(先自己答,再点答案)

测验 1

分层架构依赖应?

依赖只许向下:表现层→业务层→数据层,反向禁止,否则改一点全动。

测验 2

依赖方向关键原则?

高层策略依赖「约定/接口」,具体实现由组合根注入——这就是依赖反转。

测验 3

包按什么分组最清晰?

按功能模块分组:「改一个功能时动的文件都在一处」,比按层三大包更好维护。
