组合优于继承与依赖注入

架构与设计模式 · 课程 0008 · 预计 20 分钟

前七课都是「招式」(设计模式)。从这课开始是「内功」——不依赖具体模式、却贯穿所有代码的架构原则。今天两条:组合优于继承、依赖注入。

知识点 1:继承的问题——基类一改,全链发抖

课本教我们用继承复用行为,但现实里深继承链是著名反模式。看这个越攒越深的金字塔:

class BaseModel:
    def save(self): ...        # 基类:大家都要的
    def evaluate(self): ...


class SupervisedModel(BaseModel):     # 第二层
    def fit(self): ...


class TabularModel(SupervisedModel):  # 第三层
    def impute_missing(self): ...


class NNModel(TabularModel):          # 第四层……
    def backward(self): ...

问题链条:

  • 脆:改基类一个方法,所有后代都受影响,哪怕无关
  • 表达力差:一个模型可能「既是监督的、又能表格化、又能 NN」,多重分类只能用多继承,越搭越乱
  • 测试难:想测一个层级,得先构造一串祖先

知识点 2:组合——用「拥有」代替「继承」

组合优于继承(Composition over Inheritance):一个对象拥有其他对象(作为字段),把行为委托给它们,而不是靠血缘关系(继承)获得行为。

class Trainer:
    """组合:Trainer『拥有』一个模型 + 一个数据管道 + 一个报告器。"""
    def __init__(self, model, preprocessor, reporter):   # 依赖从外面来
        self.model = model          # 拥有
        self.preprocessor = preprocessor
        self.reporter = reporter

    def train_and_report(self, X, y):
        X_clean = self.preprocessor.fit_transform(X)
        self.model.fit(X_clean, y)
        self.reporter.emit(self.model)

现在想换预处理、换模型、换报告方式——只换对象,不改 Trainer 的代码。这就是「组合 = 可插拔」;而继承把一切焊死。

知识点 3:依赖注入——依赖从外面「传进来」

上面 __init__(self, model, ...) 把依赖从构造函数传进来,这就是依赖注入(Dependency Injection, DI)。反例是「内部 new」:

class Trainer:
    def __init__(self):
        self.model = RandomForest()      # 坏:依赖在内部写死,换不了
        self.store = FileStore()         #      测试也没法替换


class Trainer:                            # 好:依赖从外面传
    def __init__(self, model, store):
        self.model = model
        self.store = store

DI 的三个层次(越往下越强):

  • 构造器注入:构造时传入(最常用,__init__ 参数)
  • 参数注入:调用函数时传(train(model, X, y))
  • 属性注入:之后 trainer.model = ...(灵活但不直观)

知识点 4:DI 让测试脱胎换骨

依赖从外部来,测试就能「偷梁换柱」——这正是工厂那课「注册假对象」的底气:

class Trainer:
    def __init__(self, model, store):
        self.model = model
        self.store = store


def test_trainer_uses_fake_store():
    class FakeStore:                      # 测试专用的假依赖
        def __init__(self):
            self.saved = []
        def save(self, m):
            self.saved.append(m)

    fake = FakeStore()
    trainer = Trainer(FakeModel(), fake)  # 注入假的,不碰真实 IO/模型
    trainer.train(X, y)
    assert len(fake.saved) == 1          # 快速、无副作用、可断言

没有 DI 的话,测试里 new 出的真实模型和真实文件系统又慢、又不可控、还可能污染磁盘。

知识点 5:什么时候才用继承

「组合优于继承」不是说禁用继承。继承仍然合适在真正的 is-a 关系 + 要复用基类的结构/默认行为时——典型就是模板方法那课的 BaseTrainer:

用继承

是-a 关系,子类要复用父类的流程/字段。例:所有 Trainer 共享 run 骨架。

用组合

只是「需要某能力」而非「是一种」。例:Trainer 需要存储能力 → 拥有 store,而不是 extends Store。

经验法则:「是一种」用继承,「拥有一个 / 需要一个」用组合。80% 的场景答案是组合。

测一测(先自己答,再点答案)

测验 1

组合优于继承指?

让对象「拥有」其他对象、把行为委托给它们,而不是靠昂贵的遗传关系获得行为。

测验 2

依赖注入是指什么?

依赖由外面(构造器/参数)传进来,而不是类内部写死;换依赖、测依赖都容易。

测验 3

继承适合真正的?

继承留给真正的「is-a」关系 + 共享结构/逻辑;只要「需要某能力」就优先组合。
