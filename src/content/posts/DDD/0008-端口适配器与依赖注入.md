# 端口 Ports 与适配器 + 依赖注入

这是 DDD 与六边形架构系列课程笔记的第 8 课，预计 25 分钟。这是「六边形(端口-适配器)」名字的由来，也是依赖方向落地的一课。核心：**领域/应用层需要外部数据或发外部调用时，只声明一个接口(端口 Port)，真正实现(适配器 Adapter)放基础设施层，通过依赖注入接进去**。你架构课学过 DI 和接口，这里沿用，只是叫法更 DDD。

## 知识点 1:端口 = 接口,定义"要做什么"，不管"怎么做"

端口是应用核心声明的**接口**，抽象掉技术细节。比如"存用户"不问是 MySQL 还是 Postgres：

```python
from abc import ABC, abstractmethod

class UserRepository(ABC):            # 端口:只写"要做什么"
    @abstractmethod
    def save(self, user) -> None: ...
    @abstractmethod
    def find_by_id(self, user_id: str) -> "User | None": ...
```

端口在**应用层/领域层**定义；它描述的是「领域需要的操作」，别去模仿工具 API(为领域设计，不是为 ORM 设计)。[端口与适配器](https://8thlight.com/blog/damon-kelley/2021/05/18/a-color-coded-guide-to-ports-and-adapters.html)。

## 知识点 2:适配器 = 端口的实现(放基础设施)

**适配器**是端口的真实实现，塞在基础设施层，做着技术性的脏活(连数据库、调外部 API、发消息)：

```python
class SqlUserRepository(UserRepository):    # 适配器:端口的实现
    def __init__(self, db):
        self.db = db                         # 连接池/ORM
    def save(self, user):
        self.db.execute("INSERT INTO users ...", ...)
    def find_by_id(self, user_id):
        row = self.db.query(...) ; return User(row["id"], Email(row["email"]))
```

重点：**应用核心只认得 UserRepository 这个接口，不认得 SqlUserRepository**。换数据库=换适配器，不碰业务逻辑。这就是六边形：中心是应用核心，一圈适配器像六边形的边。

## 知识点 3:依赖注入——把实现"接"进接口

端口定义在里，实现在外。怎么让应用服务拿到实现？靠**依赖注入(DI)**：把适配器对象"塞"进去(架构课的 0008 学过)。这里最常见的注入点就是应用服务的构造函数：

```python
class CreateUserService:
    def __init__(self, repo: UserRepository):   # 依赖注入:只认接口
        self.repo = repo
    def handle(self, cmd):
        user = User(uuid(), Email(cmd.email))
        self.repo.save(user)                     # 用接口,不关心实现
        return user.id

# 组装(composition root):在程序入口把具体实现接进去
sql_repo = SqlUserRepository(db=connect())
service = CreateUserService(repo=sql_repo)
```

依赖方向：**CreateUserService(里)只依赖 UserRepository 接口；SqlUserRepository(外)实现接口并被注入**。核心不依赖外部，反过来外部依赖核心的接口——依赖倒置(DIP)。

## 知识点 4:为什么值钱——测试启动快、换实现容易

因为应用服务只认接口，测试时可以传一个**假的仓库**(mock)，不连真库：

```python
class FakeUserRepository(UserRepository):     # 测试用的适配器
    def __init__(self): self.data = {}
    def save(self, user): self.data[user.id] = user
    def find_by_id(self, user_id): return self.data.get(user_id)

service = CreateUserService(repo=FakeUserRepository())
service.handle(CreateUserCommand(email="a@x.com", name="Ann"))  # 不碰数据库
```

这让[单元测试](https://en.wikipedia.org/wiki/Unit_testing)又稳又快、不依赖环境。换数据库、加一个 CLI 入口，都只是"再装一个适配器"。

## 知识点 5:别过度抽象

项目提醒：滥用端口/接口会产生[假抽象](https://mortoray.com/2014/08/01/the-false-abstraction-antipattern/)、过度复杂。很多时候直接依赖具体实现完全没问题。**判断：这层真的可能被换掉/需要 mock 吗？** 需要才抽象。端口还应遵循**接口隔离**(小接口)，但也别碎到烦人。

## 测验

### 测验 1
端口(Port)本质是?
- A. 数据库
- B. 接口协议(正确)
- C. 控制器
- D. 实体类

<details>
<summary>答案与解析</summary>

**答案：B**。端口是接口，定义"要做什么"，不管"怎么做"；由适配器实现。
</details>

### 测验 2
端口的实现(连库那层)放哪?
- A. 领域层
- B. 基础设施层(正确)
- C. 应用层
- D. 控制器层

<details>
<summary>答案与解析</summary>

**答案：B**。适配器(端口实现)放基础设施层，做技术脏活；核心只认接口。
</details>

### 测验 3
把适配器塞进应用服务的方式叫?
- A. 全局变量
- B. 依赖注入(正确)
- C. 事件推送
- D. 脚本复制

<details>
<summary>答案与解析</summary>

**答案：B**。DI：把具体实现通过构造/组装注入，"接"进接口使用的应用服务。
</details>

### 测验 4
这么做的最大好处之一?
- A. 代码更长
- B. 测试可 mock(正确)
- C. 运行更快
- D. 更少文件

<details>
<summary>答案与解析</summary>

**答案：B**。用假适配器 mock，不连数据库就能跑业务测试，快且稳。
</details>
