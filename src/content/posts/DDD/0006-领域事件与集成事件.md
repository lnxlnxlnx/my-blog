# 领域事件与集成事件

这是 DDD 与六边形架构系列课程笔记的第 6 课，预计 25 分钟。当「一个聚合做了件事，别的部分想响应」时，若不把逻辑写死在执行方，就用**事件**解耦。**领域事件**是进程内的消息(用户被创建了→自动建钱包)；**集成事件**是跨进程的消息(通知外部微服务)。本课讲清两者与「事件驱动」思路，你会联想到架构课学过的观察者模式。

## 知识点 1:领域事件 =「发生了某件事」的进程内消息

聚合在执行操作时发布一个**领域事件(domain event)**，其他部分订阅并响应，彼此不直接依赖。项目里的例子：用户创建后，给用户建一个钱包。

```python
from dataclasses import dataclass, field

@dataclass
class UserCreated:                      # 领域事件:只是"发生了什么"的数据
    user_id: str
    email: str
    events: list = field(default_factory=list)   # 简单的事件列表

    def emit(self, event): self.events.append(event)
```

事件是**数据对象**(过去发生的事)，不含逻辑。策略：不用把"买完要建订单"写在 buy() 里，而是 `buy() 发布 BuyCompleted`，让外部订阅者建订单。这实现了解耦([domain event pattern](https://badia-kharroubi.gitbooks.io/microservices-architecture/content/patterns/tactical-patterns/domain-event-pattern.html))。

## 知识点 2:事件处理——一个事件多个订阅者

发布出去后，谁订阅谁处理，可有很多 handler：

```python
class EventBus:                         # 进程内事件分发器(像观察者)
    def __init__(self):
        self._handlers = {}
    def subscribe(self, event_type, handler):
        self._handlers.setdefault(event_type, []).append(handler)
    def publish(self, event):
        for h in self._handlers.get(type(event), []):
            h(event)

bus = EventBus()
def create_wallet(e): print(f"给 {e.user_id} 建钱包")
bus.subscribe(UserCreated, create_wallet)

bus.publish(UserCreated(user_id="u1", email="a@x.com"))  # 给 u1 建钱包
```

因为 handler 是「订阅」来的，发布方不知道也不关心谁在听——这正是你架构课学的**观察者模式**在 DDD 里的落地。

## 知识点 3:领域事件 vs 集成事件

项目给的关键区分：

```python
# 领域事件 domain event:进程内(同一应用/模块),内存分发
#   用途:同一领域内,一个聚合的事触发另一个聚合的动作
#   例:UserCreated → 给该用户建 Wallet

# 集成事件 integration event:跨进程(微服务/外部系统),经消息队列
#   用途:通知外部服务或微服务之间
#   例:用户注册完成 → 发邮件服务 / 通知另一个微服务
```

规则：领域事件**只在进程内**；要触达外部，再在领域事件 handler 里**发集成事件**。而且集成事件通常在该领域的所有变更落库**之后**才发([Domains vs Integration events](https://devblogs.microsoft.com/cesardelatorre/domain-events-vs-integration-events-in-domain-driven-design-and-microservices-architectures/))。

## 知识点 4:什么时候用事件、什么时候别只用事件

项目特意提醒：复杂多步骤工作流**别只靠事件**——一个事件触发另一个，链条很长很难追踪维护。此时用「一个服务/编排器」把整个流程写在一处更好(牺牲一点解耦换可维护性)。

```python
# 适合事件:一个聚合的动作,需要"附带"若干彼此独立的其他动作
#   UserCreated → 建钱包(独立,不关心顺序)

# 不适合:串行的强依赖多步骤流程,每一步都等上一步
#   用 orchestrator/service 顺着写,别用事件打散
```

选工具看场景：解耦用事件，可追踪用编排器，二者要权衡。

## 知识点 5:与事务结合 + 别滥用

多个聚合被同一事件触发的改动，通常应包在**一个事务**里(全有或全无)，项目用全局事务包裹整个流程(如 Unit of Work)。但别滥用大事务(高并发瓶颈)，可接受时用最终一致性。核心：事件是「发布-订阅」解耦，不是银弹。

## 测验

### 测验 1
领域事件在哪个范围分发?
- A. 跨进程
- B. 进程内(正确)
- C. 跨服务器
- D. 跨数据库

<details>
<summary>答案与解析</summary>

**答案：B**。领域事件是进程内消息，同一应用内分发；跨进程靠集成事件。
</details>

### 测验 2
通知外部微服务该用什么?
- A. 领域事件
- B. 集成事件(正确)
- C. 值对象
- D. 实体方法

<details>
<summary>答案与解析</summary>

**答案：B**。跨进程/外部系统用集成事件，通常经消息队列，在变更落库后发。
</details>

### 测验 3
事件 handler 机制是哪种模式?
- A. 工厂
- B. 观察者(正确)
- C. 策略
- D. 单例

<details>
<summary>答案与解析</summary>

**答案：B**。发布-订阅、一个事件多个监听 = 观察者模式在 DDD 里的落地。
</details>

### 测验 4
复杂串行多步骤流程，项目建议?
- A. 全靠事件链
- B. 一个编排器(正确)
- C. 深递归
- D. 不写

<details>
<summary>答案与解析</summary>

**答案：B**。强依赖串行流程用 orchestration 写在一处，别用事件打散导致难追踪。
</details>
