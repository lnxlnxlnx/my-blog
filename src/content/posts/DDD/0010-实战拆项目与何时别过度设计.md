# 实战拆项目与何时别过度设计

这是 DDD 与六边形架构系列课程笔记的最后一课，预计 30 分钟。前 9 课把 DDD/六边形的骨架和积木都讲了。这最后一课，我们**把整套东西用到真实 target 上**：① 用一张"拆解清单"去读 [domain-driven-hexagon](https://github.com/Sairyss/domain-driven-hexagon) 的源码轮廓；② 用同样清单读你自己 repo；③ 明确**什么时候别用这套**。想想你架构课学的"四步读法"——这里是人家的 DDD 版。

## 知识点 1:拆解一张 DDD 项目的清单

拿到一个号称 DDD/六边形的项目，按下面顺序问自己(这就是"读出它的山形")：

```python
# 1 模块划分:src/modules 下有哪些业务模块?各代表哪个 bounded context?
# 2 垂直切片:每个模块的 commands/ 里有哪些用例?queries/ 有哪些查询?
# 3 领域层:domain/ 下有哪些实体/聚合根/值对象/领域事件?
# 4 应用层:application/ 下有哪些应用服务(命令/查询处理器)?ports/ 有哪些接口?
# 5 接口适配:interface/ 下有哪些控制器、DTO?
# 6 基础设施:infrastructure/ 下有哪些仓储实现、适配器、持久化模型?
# 7 依赖方向:端口定义在哪、实现在哪、怎么注入?有没有违背"依赖向内"?
```

读一个 DDD 项目，不是逐行读，而是**先摸目录形状、再沿一个用例(垂直切片)走到底**。一个用例从 controller → command → service → domain → repository 走通，你就看懂 90%。

## 知识点 2:沿着一个用例走通(以"创建用户"为例)

项目里 create-user 这个垂直切片，翻译成 Python 形状是这样的调用链：

```python
# create-user.controller.py   ← 收 HTTP 请求
#   ↓ 转 CreateUserCommand,发给 command bus
# create-user.service.py      ← 应用服务:命令处理器
#   ├ 造 User 实体(领域)
#   ├ user repo(端口)存库 → SqlUserRepository(设施)
#   └ 发 UserCreated 领域事件
#      ↓ 事件 handler:创建 Wallet(另一个聚合)
# 结果数据 → controller → 响应 DTO 返回
```

你要能"顺着这条火车道从头走到尾"，并说出每一站(controller/service/domain/port/adapter)各干了什么、依赖朝哪。这就是读懂 DDD 项目的核心技能。

## 知识点 3:用同一套"拆解脑"看你自己的代码

把你 repo 里最复杂的一个脚本当靶子，问：它该不该按这套拆？比如——

```python
# 现状:一个 main.py 里 又收输入 又算业务 又连库 又拼输出
# 拆解成 DDD 的提问:
#   - 有没有"领域实体/不变量"值得单独成类?(值对象/实体)
#   - 读写是否该分离?(命令/查询)
#   - 数据库访问是否该用接口包一层,方便测试/换库?(端口/适配器)
#   - 外部 I/O(发邮件/HTTP)是否隔离?(适配器)
```

不必全部上，先挑"确实受益"的部分拆。小项目往往只用到：实体/值对象 + 应用服务 + 一个简单仓储端口，分层没那么高。[别把自己写成年年贫血模型](https://martinfowler.com/bliki/AnemicDomainModel.html)。

## 知识点 4:何时不用的明确清单

项目反复强调，这是**推荐非铁律**。别硬套的场景：

- 纯 CRUD、业务规则极少的小应用 → 完整 DDD 是过度设计
- 一次性脚本、原型 → 单层直接写
- 只有一个团队、不会拆微服务 → 模块化/端口不必那么彻底
- 技术完全锁定不会换 → 抽象数据库那层收益低

判断口诀：**抽象只在"会变/会被换/需要 mock"的地方值钱**；不确定时，先写简单，等出现"换库/加端口/多团队"的真实需求再补抽象，而不是从第一天堆满([假抽象](https://mortoray.com/2014/08/01/the-false-abstraction-antipattern/))。

## 知识点 5:把"读懂"变成可验证的一步

读一个真实 DDD 项目最后给自己交差：能画一张"模块→分层"示意图，并能回答"如果我加一个新用例(给用户加积分)，改动会落在哪些文件、依赖朝哪"。答得出这个，你就真读懂了，而不再是"每个词都认识但串不起来"。

## 测验

### 测验 1
读懂 DDD 项目先做什么?
- A. 逐行读
- B. 摸目录形状(正确)
- C. 先读测试
- D. 先跑起来

<details>
<summary>答案与解析</summary>

**答案：B**。先摸 modules/domain/application/interface/infrastructure 目录形状，再沿一个用例走通。
</details>

### 测验 2
最简单 CRUD 小应用该用它吗?
- A. 必须用
- B. 不必用(正确)
- C. 只能用
- D. 看目录

<details>
<summary>答案与解析</summary>

**答案：B**。纯 CRUD/小项目硬套完整 DDD 是过度设计；可挑部分受益的用。
</details>

### 测验 3
抽象数据库接口什么情况下值钱?
- A. 永远值钱
- B. 会换库/需 mock(正确)
- C. 从不值钱
- D. 看代码长度

<details>
<summary>答案与解析</summary>

**答案：B**。抽象在"会变、会被换、需要 mock"时才值钱；技术锁死时收益低。
</details>

### 测验 4
读懂一个项目最终要能?
- A. 背目录
- B. 讲清改动影响(正确)
- C. 跑通即可
- D. 抄一遍

<details>
<summary>答案与解析</summary>

**答案：B**。能画出分层并回答"加新用例改动落在哪些文件、依赖朝哪"，才算真读懂。
</details>
