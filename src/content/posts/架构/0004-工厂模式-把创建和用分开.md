# 工厂模式:把创建和用分开

上一课你见到了「注册表 + 工厂」的影子。这课把它放大讲透。**工厂模式(Factory Pattern)**是整个创建型模式的代表,也是 AI 生成的代码里**出现频率最高**的套路——名字叫 `make_xxx`、`create_xxx`、`build_xxx`、`get_xxx` 的函数,基本都是工厂。

## 知识点 1:问题——到处 new 具体类

假设没有工厂,代码会写成这样——调用方到处「new 具体类」:

```python
def train_svm(data):
    trainer = SVMTrainer()          # 直接 new 具体类
    return trainer.run(data)


def train_logreg(data):
    trainer = LogisticRegressionTrainer()   # 又一个具体类
    return trainer.run(data)


# 想「全局把默认模型从 SVM 换成决策树」?
# → 你得上百个地方,逐个把 SVMTrainer() 改成 TreeTrainer()
```

问题:创建细节(怎么 new)和使用逻辑(怎么用)**混在一起**。两者一起变的时候,代码到处要改。

工厂做的事很简单:**把「怎么造对象」集中到一个地方**。使用方只问一句话:「给我一个叫 X 的东西」。

## 知识点 2:简单工厂(Simple Factory)

最基本的一档:一个函数,按参数返回不同对象。这是「集中创建」的最小形态:

```python
def make_trainer(name):
    """简单工厂:把『按名字造训练器的逻辑』集中在这一处。"""
    if name == "svm":
        return SVMTrainer()
    elif name == "logreg":
        return LogisticRegressionTrainer()
    else:
        raise ValueError(f"未知训练器: {name}")


# 调用方(所有地方都长这样):
trainer = make_trainer("svm")       # 只认名字,不认具体类
trainer.run(data)
```

好处立竿见影:以后想改默认实现、想加日志、想加缓存,只动 `make_trainer` 一处。**存在的代价**:每加一种训练器,还得回来改 `make_trainer` 的 if。

## 知识点 3:注册表工厂——AI 代码的标准答案

AI 生成的代码几乎都是用「**注册表 + 工厂函数**」把上面那个 if 也干掉——新增类不用碰工厂。这就是你第一课见过的 `TrainerRegistry`,拆开看:

```python
class TrainerRegistry:
    """一个全局的『名字 → 类』登记处。"""
    _registry = {}

    @classmethod
    def register(cls, name):
        """装饰器:用 @TrainerRegistry.register('svm') 就能登记。"""
        def wrap(trainer_cls):
            cls._registry[name] = trainer_cls     # 把类存进字典
            return trainer_cls
        return wrap


@TrainerRegistry.register("svm")
class SVMTrainer(BaseTrainer): ...     # 定义完类,顺手登记

@TrainerRegistry.register("logreg")
class LogisticRegressionTrainer(BaseTrainer): ...


def make_trainer(name):
    """工厂:从登记处取类,再实例化。"""
    try:
        return TrainerRegistry._registry[name]()  # 字典取值 → new
    except KeyError:
        raise ValueError(f"未知训练器: {name}") from None
```

现在加「决策树训练器」只需**新增一个类 + 一行装饰器**,`make_trainer` 永远不用改。这就是「创建 vs 使用」解耦的终极形态——**这也是为什么 AI 生成的代码里到处是 register/make_xxx**:新功能以「注册」的方式插进来,不破坏已有代码。

## 知识点 4:工厂方法(Factory Method)——让子类决定

更「面向对象」的一档:把「创建逻辑」本身放回类里,子类各写各的。当不同子类的构建方式差异很大时用它([官方讲解](https://refactoringguru.cn/design-patterns/factory-method)):

```python
from abc import ABC, abstractmethod


class BaseTrainer(ABC):
    @classmethod
    def create(cls, config):          # 工厂方法:公共骨架
        """按配置造好一个训练器(子类各自实现 _build)。"""
        model = cls._build(config)
        return cls(model)

    @abstractmethod
    def _build(self, config): ...     # 具体怎么构建,子类填


class SVMTrainer(BaseTrainer):
    def _build(self, config):
        return SVC(C=config.get("C", 1.0))


class TreeTrainer(BaseTrainer):
    def _build(self, config):
        return RandomForest(n_estimators=config.get("n", 100))


svm = SVMTrainer.create({"C": 0.5})    # 同一个 create,行为由子类决定
tree = TreeTrainer.create({"n": 200})
```

区别一句话:**简单工厂是「一个函数管所有类」;工厂方法是「每个类自己决定怎么被创建」**。前者写起来快,后者扩展更自然。

## 知识点 5:抽象工厂(Abstract Factory)——一整套配套对象

当你要造的是一组**必须配套**的对象(不能混搭)时用抽象工厂([官方讲解](https://refactoringguru.cn/design-patterns/abstract-factory))。经典例子:GUI 控件一族——按钮/菜单/文本框必须来自同一套风格:

```python
class GUIFactory(ABC):
    @abstractmethod
    def create_button(self): ...
    @abstractmethod
    def create_menu(self): ...


class WindowsFactory(GUIFactory):      # Windows 风格一族
    def create_button(self): return WindowsButton()
    def create_menu(self):   return WindowsMenu()


class MacFactory(GUIFactory):          # Mac 风格一族
    def create_button(self): return MacButton()
    def create_menu(self):   return MacMenu()
```

使用方只认 `GUIFactory`,拿到的一定是「配套」的一套,不会出现 MacButton 配 WindowsMenu。这个模式在你的日常里少见,**认得出来就行**。

## 知识点 6:工厂帮了你一个暗中的忙——测试

因为创建被集中了,测试时就能「偷梁换柱」:注册一个假的训练器,不碰真实模型:

```python
def test_pipeline():
    # 注册一个假训练器,完全不训练,只测流程
    class FakeTrainer(BaseTrainer):
        def fit(self, model, x, y): return None
        def evaluate(self, model, x, y): return 1.0

    TrainerRegistry._registry["fake"] = FakeTrainer

    trainer = make_trainer("fake")    # 工厂照常工作,管道全走通
    assert trainer.run(data) == 1.0
```

没有工厂的话,每次测试都得临时 new 一个真的模型——又慢又不可控。这就是「解耦创建」付给可测试性的红利。

## 知识点 7:什么时候别用

- 整个项目就**一种**对象、毫无替换迹象 → 直接 new,别建工厂(YAGNI)
- 创建逻辑简单到只有一个 `return Xxx()` → 工厂是多余的一层
- 判断标准:创建逻辑**会不会变化/扩展**?会,才值得为它建一条缝。

- D. 静态的方法决定

<summary>答案与解析</summary>

### 测验 3
AI 代码工厂常配什么?
- A. 一个单例类对象
- B. 一个注册表字典(正确)

- D. 一根异步任务队列

<summary>答案与解析</summary>

</details>
