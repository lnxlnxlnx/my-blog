# 组件与构建系统

上一课你跑了 `idf.py build`。这一课回答:**这几条命令背后,CMake 是怎么把整个工程拼起来的?**读懂构建系统,是读懂 xiaozhi 这种几十个组件的工程的钥匙。

## 知识点 1:三个 CMakeLists 各管一段

IDF 的构建是三层嵌套的 CMake,你的 00_basic 里正好各有一个:

```cmake
# ① 顶层:声明这是什么项目
cmake_minimum_required(VERSION 3.16)
include($ENV{IDF_PATH}/tools/cmake/project.cmake)  # 拉进 IDF 全家桶
project(00_basic)
```

```cmake
# ② main/ 组件:声明源文件 + 头文件目录
idf_component_register(SRCS "main.c"
                    INCLUDE_DIRS ".")
```

**组件(component)** 是 IDF 的复用单位:`idf_component_register` 声明"我这个组件有哪些源文件、暴露哪些头文件"。别的组件想用它,就在自己的 CMakeLists 里 `REQUIRES xxx`。

## 知识点 2:组件从哪来

| 位置 | 来源 | 进不进 git |
|------|------|------------|
| `main/` | 你自己写的 | ✅ |
| `components/` | 你手动放的(vendored) | ✅ |
| `managed_components/` | `idf.py` 按 `idf_component.yml` 自动下载 | ❌(已 gitignore) |
| IDF 内置 | 随工具链自带(driver、freertos…) | — |

> 这就是为什么上次 git 整理把 `managed_components/` 移出版本控制——它是"包管理器"的产物,`idf.py build` 会自动重新拉。

## 知识点 3:sdkconfig 是怎么被消费的

菜单里选的东西最终变成 `sdkconfig` 里的 `CONFIG_XXX=y`,而代码里用 `#ifdef CONFIG_XXX` 决定编译哪份代码。组件 CMakeLists 里再用 `idf_component_register(... REQUIRES esp_driver_gpio)` 引入依赖。

```c
// 这就是为什么改配置要重新编译
#ifdef CONFIG_ESP_SYSTEM_PANIC_PRINT_BACKTRACE
    esp_backtrace_print();
#endif
```

## 动手实践

在 `basic_routines/00_basic` 里执行 `idf.py menuconfig`,随便改一个开关(比如日志级别),保存后 `git diff sdkconfig`——你会看到**一行文本的差别**,这就是"配置可追踪"。

## 测验

### 测验 1
组件声明源文件和头文件的宏是?
- A. idf_component_register(正确)
- B. project()
- C. add_library

<details>
<summary>答案与解析</summary>

**答案：A**。idf_component_register,在组件自己的 CMakeLists.txt 里。
</details>

### 测验 2
managed_components/ 里的组件来自?
- A. 自动下载(正确)
- B. 手动拷贝
- C. 自己编写

<details>
<summary>答案与解析</summary>

**答案：A**。按 idf_component.yml 由 idf.py 自动下载,不进 git。
</details>
