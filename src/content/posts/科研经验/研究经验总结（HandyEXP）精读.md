# 研究经验总结（HandyEXP）精读：王鑫涛的科研方法论

> 本文是 [王鑫涛（Xintao，Real-ESRGAN / BSRGAN 作者）《研究经验总结-HandyEXP》](https://www.yuque.com/xinntao/nm1yxs/teq1y5dqiivvv9lr) 的精读笔记，按原文"理念 / 实操 / 流程 / 启发"四部分结构压缩整理，要点尽量保留原意，细节推荐阅读原文。
> **HandyEXP 含义**：Exp² = Experiment - Experience，即"把实验经验变成随手可用的工具"。

---

## 一、前言：这份总结的定位

**为什么写**：

- **经验是可复制的**——把自己踩过的坑记录下来分享，对他人有帮助。
- **经验是可迭代的**——像做实验一样，不断尝试、反馈、迭代，帮后面加入的团队成员成长。
- **把有限的精力投入到更有价值的思维活动中去**——将日常流程规范化、标准化、自动化，大脑才能腾出精力思考更好的 idea 和更全面的实验设计。

**四个部分，不断迭代**：

| 部分 | 定位 |
|------|------|
| 理念篇 | 影响比较大的认知，"授人以渔" |
| 实操篇 | 试错后被选中的实践，"适合我们普通人的'笨'方法" |
| 流程篇 | 日常流程的记录，方便后续查阅 |
| 启发篇 | 阅读中看到的可借鉴经验，"他山之石，可以攻玉" |

**不是什么**：不是形式主义（觉得是表面功夫说明理解有偏差）；不是空谈教条（觉得空洞就一起细化，核心是灵活掌握）。

## 二、理念篇：认知先于行动

### 核心理念

**1. 高频操作必须低成本**

日常研究中的高频操作会无意识占据大量时间，必须把成本降到最低，理由有三：

- **得到更多输入，发现新东西**：小操作成本高，大脑就懒得看；成本降到"随手就能看"，信息输入多了，潜意识会自动思考，新想法会蹦出来。典型例子：**看结果图**——在 VSCode 里一张张点开看，等待久、切换慢、信息密度低，于是用批量看图软件（作者为此写了 [HandyView](https://github.com/xinntao/HandyView)）或网页工具整体呈现，看多了才能发现"猫腻"、提出新假设。
- **节省时间**：① 尽量写脚本替代手工操作（"感觉的时间耗费和实际的时间耗费是不一致的"，手工改数据远比想象中耗时，脚本还能复用，现在有 GPT4/Copilot 写脚本很方便）；② "感觉麻烦的地方，一定是可以优化的"——比如反复复制粘贴，用 win+v（Windows 剪贴板历史）或 PasteNow（macOS）解决。
- **降低沟通成本**：高频讨论的东西（尤其是实验）要有统一的**命名体系**，实验序号成为大家的共识代号，不用反复确认"说的是哪个实验"。

**2. 记忆是不可靠的，大脑是情绪化的**

- 人往往会记岔具体的 setting 和结论，讨论时会带偏分析。
- 依赖主观评价的结果（GAN 复原、图像生成）受情绪影响极大：情绪好看到有利的一面，情绪差看到不利的一面。
- 对策：**实验 setting 和分析结论必须记录文档**（实验表格）；**validation 要定标准、多看例子**，尽量给出客观结论，主观评价也要明确"重点观察什么"。

**3. 要有 owner 意识**：把项目当作自己的来做，遇到问题先想"为什么不 work，是哪里的假设/分析出问题了"，而不是"这个东西不 work"。

**4. 快速迭代**：先有——抓住主要矛盾先做出来，不能为了完美迟迟出不来；有了初版就有了框架，才能不断填充完善。

### 其他理念

- **要可大可小**：大要抓住宏观（项目目标、研究贡献、实验 RoadMap、排期），抓主要矛盾，防止"细节的黑洞"和钻死胡同；小要做好细节（方案、描述逻辑、代码细节），方案能否实现靠细节。把握尺度靠经验、敏感、多想。
- **是正确的趋势吗？**：技术是往更好方向发展的。要往正确的发展方向去思考方法；站在未来回看，判断是否有必要、有价值、是否阻碍技术进步。

## 三、实操篇：具体怎么做

### 整体流程

区分四个概念：**Assumption（假设）、Expectation（预期）、Observation（观察）、Analysis（分析）**。反观自己的想法处于哪个阶段；任务是要有更多 Assumption 并得到验证或 insights；**不止于 Observation，要 Analysis**。

### 开发环境（善用工具）

- 编辑器插件：静态检查（pep8/flake8）、格式化（yapf）、import 排序（isort）、GitHub Copilot、Code Spell Checker（检查拼写）
- **pre-commit**：提交前强制检查格式，减少错误、保证团队一致（每个 git 项目要跑一次 `pre-commit install`）
- **tmux**：多窗口管理，保持远端程序后台运行
- **zsh（oh-my-zsh）**：命令历史、自动补全

### 代码规范

**目的**：看得懂、解耦复用可迭代、减少 bug。这是习惯问题，不会花太多时间。

**命名宗旨：精、准、统一，便于理解**：

| 对象 | 规则 |
|------|------|
| 函数名/变量名/文件名 | 小写+下划线，如 `ffhq_dataset.py` |
| 类名 | CamelCase，如 `FFHQDataset` |
| 常量 | 大写+下划线 |
| 私有函数 | 下划线开头 |
| 避免 | 单字符、aa/bbb 无意义名、奇怪缩写、过长函数名 |
| 函数命名 | 动宾结构，如 `setup_optimizers` |

其他：缩进 4 空格、行宽 120、import 排序交给 isort；**函数默认参数不要用 list/dict 这类 mutable 对象**（用 tuple() 或 None），否则会悄悄变化引发 bug；重要参数尽量不给默认值。

**注释**：逻辑块写明作用；hard code 必须注释（一句话，方便以后的自己）；shape 变换复杂处边读边注释；公共函数要有详尽 docstring（只读 docstring 就能合理使用接口、推测逻辑）。

**单元测试**：暂不做完整单测（平衡效率），但要有单测思想——写完新 dataloader 或网络结构，至少单测一把能跑。

**解耦复用**：少重复多复用；代码重复要考虑剥离复用；不复用的坏处是"短时间的方便，长时间的麻烦"——改 bug 要每个文件都改，容易漏改引入新 bug。

**分层代码规范**（回应"研究代码变化太快没法遵守"）：

1. **核心公用代码**：必须遵守规范、详尽文档、release 前有测试
2. **开发代码**：主要是格式规范（自动化减少 bug）；快速验证时可以复制文件，但要定期清理，能用参数控制的就用参数
3. **临时代码**：用完及时清理；多次使用说明它不是临时的，要变成工具代码

### 使用 git 管理代码

- 分析问题时乱改、新想法随手试，没有 git 就乱了；**git 能 track 历史、方便 debug、备份、强制清理代码**。不要 copy 多份代码分开维护（改 bug 会漏）。
- **多提交 commit**：每个大改动、每/组实验都提交；写有意义的 commit message（方便回溯）。
- **多人合作早 merge**，差距越大越难合并；及时 pull 与 push（早上 pull，大更新结束 push）。
- 共用 repo 的大改动要告知大家；本地大改动注意**向后兼容**（如 dataset 里没在 `__init__` 声明的变量后面用了，每个 epoch reload dataloader 会炸）。
- **定期回顾代码**：该抽象的抽象、该完善的完善（hard code、命名注释）、该剥离的剥离到基础公有库。
- 给基础公有库提交修改要走 **PR**：开新 branch → pull 最新 master → 修改提交 PR → master 更新及时 pull 解决冲突 → PR 颗粒度要细。

### 使用【实验表格】管理实验

**为什么**：记忆不可靠，idea、预期、setting、分析结果都要记录；收敛到**一份**表格（多份表格维护成本高）；讨论以实验表格为核心。

**要点**：

- 实验目的和预期在设计前就列清楚
- **跑实验前先把实验表格整理好**（帮自己完整细致思考 variants），重要的先列，全面考虑，按资源排优先级
- 新 idea 及时记录在表格下方
- **实验命名要认真对待**：数字序号打头（方便讨论指代、文件夹排序、tensorboard 比较、finetune 引用如 `3012500kft`）；核心改动体现在命名上；分组实验一段时期后重新整理命名，避免名字过长
- setting 和分析记录在边上，要客观；**做了实验就要有结论**，即使结论模糊也要下启发性的结论并解释

**实验设计指导思想**：

- **保守的 + 激进的，同时做**：保守路线可能都困在局部最优点，要有大步子实验跳出来（可能运气爆棚）
- **控制变量是灵活的**：A、A+B、A+B+C 也是控制变量（先对 B/C 谁更优做概率判断，在更优的基础上验证 C）；pre-trained model 作为 A 不断变化并不影响控制变量
- **概率思维**：idea work 与否是条件概率，不是 0-1。跑实验前就有概率判断；不能判定一定 work 或一定不 work，只能基于经验、逻辑和文献给出概率
- **配置文件**：善用对比实验 configs——人对于差异很敏感，内容看十遍都不一定看出差异，对比能减少错误

### 验证集

- **有区分度**：核心功能例子 + badcases 例子（保证改进后核心功能不消退，又能看出改进效果）
- **分阶段**：每个阶段关注的问题不同，验证集也不同
- **分层次**：核心验证集（数量小、只覆盖核心点、验证快）+ 全面验证集（核心验证有苗头后再跑）
- **尽早 validation**：不能等实验跑完再看，要多看中间结果，早发现问题早解决

### 论文文献管理

推荐 **Zotero + OneDrive**，以及 ReadPaper。（原文此处待更新）

### 讨论与汇报

- **讨论前有 Outline**：列清楚讨论哪几块、预期什么结论；有深入思考可以改路径，但要有清晰论据
- **讨论中解决问题**：形成下一步具体方案，不抱着"回去再想"的态度
- **讨论后总结**：回顾要点和 Action Items，记录下次首先要同步的几个问题
- **预期管理**：通过更多信息来管理预期（不是隐瞒），及时同步风险项

### 利用 GPT4/Copilot

写代码、改文章一定要用；积极拥抱新技术、新工具。

### 有不同的流程怎么办？

一起交流迭代，吸收更好的方式。新同学先按这套流程来，好与不好试了才知道；**规范不会影响创造性**——创造性在 idea 和分析层面，规范反而让你更细致，发现更多之前发现不了的问题。

## 五、启发篇：他山之石

- **"迈开你的两脚，去做调查，调查就是解决问题"——毛泽东**：研究卡住、无从下手时，就去调查：看相关论文、分析实验、和别人讨论，"看着看着就有思路了"。
- **"把本来的平平淡淡，看得异军突起，这样才能有创造性"——王沪宁**：对研究中"有趣的或违背直觉的"现象要深入挖掘、主动赋予深刻含义。大部分可能不 work，但不能因此放弃思考。ResNet 的 shortcut 之前 highway networks 也探究过，但没人深入挖掘。
- **"设计一些能带给你点什么的实验，关键的数据往往来自对照组"——Katalin Karikó（Langer 博士）**：① 要设计即使成功也能推动前进的实验，很多实验即使全部按预期发生也不会有新结果——那是实验设计问题；② 多分析已有实验（尤其 baseline）的好 cases 和坏 cases，找共性；③ **成功的经验是一部分，更重要的是失败的经验**——"成功的实验都是相似的，不成功的尝试各有各的不成功，后者才能更有效地告诉我们哪里有坑"。

## 六、我的收获

这份总结最有价值的地方在于：**它把科研从"凭感觉做事"变成了一套有记录、有标准、可迭代的系统**。对我最有用的是三条：高频操作必须低成本（工具先行）、实验表格 + 实验命名（让讨论有共同语言）、概率思维（用条件概率替代"行/不行"的二元判断）。原文仍在持续更新，建议收藏原文，每隔一段时间回看。
